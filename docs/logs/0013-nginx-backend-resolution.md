# BUG-002: обновление адреса backend

Задача: nginx должен повторно разрешать имя backend после смены IP контейнера без перезапуска frontend, сохраняя путь и query.

Статус: исправление реализовано и проверено в `fix/nginx-backend-resolution` от `dev`, готово к пользовательскому review.

Решение: resolver Docker DNS 127.0.0.11 с valid=1s, resolver_timeout=2s, proxy_connect_timeout=2s и имя backend в переменной proxy_pass. URI в proxy_pass не задаётся, поэтому исходные путь и query передаются целиком. Альтернатива с zone/resolve требует nginx не ниже 1.27.3 и для единственного backend избыточна. Основание: [proxy_pass](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass), [upstream resolve](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#resolve).

Первоначальный результат: конфигурация и README обновлены; `go test ./... -cover`, `go test -race ./...`, `go vet ./...` прошли. Сетевой EOF Docker Hub блокировал запуск контейнеров, поэтому предел восстановления 5 секунд оставался непроверенным. Ограничение снято следующей интеграционной проверкой.

Проверка выполнена на отдельном Compose-проекте с тестовой БД, локальными образами приложения и nginx 1.30.6. Для исходной и исправленной конфигураций стенд создавался заново. Backend удалялся; его прежний IP занимал временный контейнер, затем backend пересоздавался. Подтверждена смена адреса с 172.19.0.3 на 172.19.0.5 и ответ Docker DNS с новым IP. У frontend до и после совпали ID и StartedAt; после смены IP ни перезапуска, ни reload nginx не было.

Исходная конфигурация продолжала возвращать 502 во всех 30 запросах за 6,019 секунды после готовности backend и обновления DNS. Исправленная конфигурация вернула 200 на первом запросе за 0,008 секунды, что укладывается в целевые 5 секунд. Это измерение одного прогона, а не гарантия при любых сетевых отказах. После смены адреса успешно проверены POST 201, существующие и новые ссылки GET/HEAD 302, отсутствие тела HEAD, точный Location с query/fragment, запросы без query, с пустым query и percent-encoded значениями.

Для проверки именно передачи URI временный echo-backend в той же изолированной сети вернул полученные метод и request_uri в заголовках. Все 12 сочетаний GET/HEAD/POST и четырёх URI (включая пустой query, несколько параметров, percent-encoding и /api/links) совпали побайтно. Маршрутизация проверялась с конфигурацией nginx из ветки без подмены proxy_pass. Вспомогательные скрипты проверки остаются локальными; orchestration-инструменты в проект не добавлялись.

Финальные проверки: `nginx -t`, `go test ./... -cover`, `go test -race ./...`, `go vet ./...` — успешно. Ветка не слита в dev.
