# SQL через версионированные миграции

- Задача: исправить замечание code review — убрать создание схемы из backend и хранить SQL-миграции в корневой папке migrate рядом с core и adapters.
- Решение и статус: требование принято пользователем; исправление реализовано и проверено в той же ветке feature/create-short-link. Повторный пользовательский review ожидается; слияние в dev не выполняется.
- Обоснование: схема должна изменяться отдельно от запуска приложения с учётом применённых версий. Используется golang-migrate v4.19.1 в одноразовом контейнере Compose; новые runtime-зависимости Go не нужны.
- История решения: заменяет инициализацию схемы в репозитории, описанную в логе 0005. Исходная запись сохраняется как история отклонённого на review решения.
- Границы: начальная up/down миграция, команды Makefile, запуск миграций до backend, удаление Initialize и связанных тестов. API не меняется.
- Совместимость: первая миграция использует CREATE TABLE IF NOT EXISTS для таблицы прежней реализации; существующие строки сохраняются, версия начинает учитываться в schema_migrations. Это рассчитано на прежнюю таблицу с теми же колонками, не на произвольную существующую схему.
- Альтернативы: SQL в docker-entrypoint-initdb.d применяется только при пустом томе и не обеспечивает версионированное обновление; собственный движок миграций добавляет лишнюю логику. Выбран готовый golang-migrate.
- Критерии готовности: backend не выполняет DDL; up/down SQL лежат в migrate; Compose блокирует запуск backend при ошибке миграций; проверены up, повторный up, down/up на изолированной базе и сохранение данных старой таблицы; test/race/vet проходят.
- Результат: добавлены корневой migrate с up/down SQL, сервис golang-migrate и зависимость backend от успешных миграций, цели Makefile migrate-up/migrate-down/migrate-version. Удалены Initialize, embed SQL в репозитории и тесты удалённой инициализации. Обновлены README, архитектура, продукт, VERSIONS.md, AGENTS.md и shorter-go. Go-зависимости не менялись.
- Проверки Go: make check успешно выполнил test с покрытием, race detector и vet. Тесты репозитория Save сохранены и проходят; покрытие сервиса, репозитория и HTTP-обработчика остаётся 100% операторов. Навык shorter-go прошёл quick_validate.py; поиск подтвердил отсутствие DDL и Initialize в коде cmd/core/adapters. Docker Compose config, сборка backend и загрузка закреплённого образа мигратора успешны.
- Проверки PostgreSQL: make migrate-up применил версию 1 к прежней таблице; старые строки сохранены, версия 1 и dirty=false подтверждены SQL. make migrate-version вернул 1, повторный make migrate-up — no change. На отдельной случайно именованной тестовой базе выполнены up, повторный up, down 1, up с проверками наличия таблицы и версии. Тестовая база удалена; основной том не откатывался.
- Проверки Compose/HTTP: штатный up --wait сначала завершил migrate с кодом 0, затем запустил backend; POST вернул 201, код найден в PostgreSQL с точным исходным URL. В изолированном Compose-проекте SQL с вызовом несуществующей функции завершил мигратор с ошибкой, backend остался в состоянии created и не запускался. Тестовый проект, его том и временные файлы удалены. Основные контейнеры остановлены, основной том сохранён.
- Особенности среды: при двух первых попытках создания Docker-контейнера возникал временный EOF соединения с daemon; повторные проверки завершились успешно.
- Ограничения: down начальной миграции удаляет данные links; совместимость старой таблицы предполагает прежнюю структуру. Автоматическое исправление dirty-состояния не выполняется. Редирект по короткой ссылке остаётся вне задачи.

## Финальная проверка и приёмка

Пользователь одобрил задачу и разрешил слияние в dev при успешной финальной проверке. Финальная проверка завершена успешно:

- `go test -count=1 ./... -cover`, `go test -race -count=1 ./...`, `go vet ./...` прошли без ошибок; тесты выполнены без использования кеша результатов.
- Compose config и сборка backend успешны. Миграция завершилась с кодом 0, schema_migrations содержит версию 1 с dirty=false; повторный up вернул no change.
- GET /healthz вернул 200 и ok; POST /api/links — 201, возвращённый код найден в PostgreSQL с точным исходным URL. Некорректный URL вернул 400 без изменения количества строк.
- После down/up сервер готов, созданная запись сохранилась. Контейнеры остановлены, основной том сохранён с проверочными записями.

Итог: задача реализована, проверена и принята пользователем; ветка готова к разрешённой интеграции в dev. Для слияния используется fast-forward, чтобы сохранить точно проверенный код без конфликтных изменений. Stage остаётся на прежнем коммите; отправка на удалённый сервер не выполняется. Ограничения редиректа и отката данных остаются описанными выше; новый этап не начинается.
