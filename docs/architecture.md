# Архитектура

Backend использует Go: `net/http` для HTTP, `log/slog` для логов, pgx/v5 для PostgreSQL. Точка входа `cmd/shorter` собирает зависимости, проверяет соединение с БД и запускает HTTP-сервер. При остановке сервер завершает активные запросы перед закрытием пула.

Структура Ports & Adapters:

- `core/models` — модель Link; `core/ports` — интерфейсы хранилища, генератора кода и сокращения ссылки.
- `core/services` — проверка URL, создание кода, сохранение и повтор при коллизии; ядро не зависит от адаптеров.
- `core/errors` — ошибки ядра, импортируемые как `cerrors`.
- `adapters/handlers` — HTTP и JSON, локальные DTO в `dto`.
- `adapters/repositories/postgres` — параметризованный INSERT через pgx, без управления схемой.
- `adapters/codegen` — генерация 9 случайных байт через crypto/rand, кодирование в 12 символов base64url.
- `migrate` — версионированные SQL-файлы up/down, применяемые golang-migrate отдельно от backend.

Принятое хранилище — PostgreSQL (заменяет первоначальный ориентир in-memory). Таблица `links` хранит `code` (первичный ключ) и `original_url`. Схему создаёт миграция `migrate/000001_create_links.up.sql`, откат описан в соответствующем `.down.sql`. Применённую версию и dirty-состояние учитывает golang-migrate в `schema_migrations`; движок блокирует конкурентное применение миграций. Backend не выполняет DDL.

Первая миграция допускает существование совместимой таблицы из ранней реализации, сохраняя строки. Произвольные отличия старой схемы не исправляются автоматически. Откат первой миграции удаляет таблицу и её данные. Изменения схемы добавляются следующими нумерованными файлами; применённые миграции не переписываются.

Уникальность кода обеспечивается атомарным `INSERT ... ON CONFLICT (code) DO NOTHING`. Нулевое количество вставленных строк преобразуется в ошибку конфликта ядра. Сервис делает до пяти попыток; успешный ответ возможен только после сохранения. Один URL можно сократить несколько раз.

Маршруты: `GET /healthz` проверяет HTTP-процесс; `POST /api/links` создаёт ссылку. Редирект пока отсутствует. Настройка `BASE_URL` задаёт публичный префикс; допускается префикс пути, но без query, fragment и credentials. Таймаут операции сокращения — 5 секунд; ошибки зависимостей не раскрываются HTTP-клиенту.

Сервис проверяется Table-Driven тестами с gomock, репозиторий — с pgxmock, обработчик — через httptest и gomock. `make generate` генерирует моки портов закреплённым в go.mod инструментом mockgen. `make check` запускает тесты, race detector и vet; все три обязательны перед коммитом.

Dockerfile собирает статический Go-бинарник в отдельном этапе и запускает его в Alpine от непривилегированного пользователя. Compose запускает PostgreSQL 17, одноразовый контейнер `migrate/migrate:v4.19.1` и backend. Мигратор ждёт готовности PostgreSQL через `pg_isready`, backend — успешного завершения мигратора (`service_completed_successfully`). Ошибка миграции блокирует запуск backend. SQL монтируется в мигратор только для чтения; в образ приложения не включается.

Для базы используется именованный том; порт на хост не публикуется. Backend и мигратор получают согласованные PG-переменные из общего блока Compose. Мигратор использует PostgreSQL-драйвер своего CLI и права на DDL; приложение продолжает работать через pgx. Для локального MVP используется один пользователь, но права CREATE backend больше не нужны для его кода.
