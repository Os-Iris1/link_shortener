# Разработка Shorter на Go

- Используй Go и стандартную библиотеку; HTTP — `net/http`, логи — `log/slog`.
- Соблюдай Ports & Adapters: ядро размещай в `core/models`, `core/ports`, `core/services`, `core/errors`; ошибки ядра импортируй как `cerrors`. Адаптеры размещай в `adapters/repositories`, `adapters/handlers`, `adapters/middlewares` по необходимости; DTO и DAO допустимы внутри соответствующего адаптера. Ядро не импортирует адаптеры, pgx или HTTP-типы. PostgreSQL использует pgx.
- Используй PostgreSQL как хранилище MVP. Это заменяет прежний ориентир in-memory по решению пользователя; см. `docs/logs/0002-docker-infrastructure.md`.
- Схему PostgreSQL изменяй только через версионированные SQL-миграции up/down в корневой папке `migrate` рядом с `core` и `adapters`. Используй golang-migrate; backend и репозитории не выполняют DDL при запуске. Проверяй применение, повторный запуск и откат на отдельной тестовой базе. Применённые миграции не переписывай, новые изменения добавляй следующей версией без дат в именах файлов.
- Поддерживай запуск через Docker и Docker Compose; backend должен ждать успешного применения миграций.

Это перенос читаемых ориентиров повреждённого раздела исходного `AGENTS.md`. Не выводи дополнительные ограничения из утраченных формулировок; контекст переноса — `docs/logs/0001-extract-project-skills.md`. Проектные пути отсчитываются от корня репозитория.

Сервисы и репозитории покрывай Table-Driven unit-тестами. Для сервисов используй gomock, для репозиториев — pgxmock; моки портов генерируй через `make generate`. Поддерживай Makefile с целями test, race, vet и check. Проверяй новую бизнес-логику unit-тестами. Выбирай проверки соразмерно изменению. Для поведения приложения проверяй критерии готовности; для исправления ошибки — исходный сценарий воспроизведения.

Для изменений Go-приложения выполняй:

```sh
go test ./... -cover
go vet ./...
```

Обязательно выполняй `go test -race ./...`. Перед каждым коммитом должны успешно пройти тесты с покрытием, race detector и go vet: `make check`. Если C toolchain или другая необходимая среда недоступна либо проверка падает, не создавай коммит и сообщи об ограничении.

В итоговом отчёте кратко укажи изменения, фактически выполненные проверки и существенные ограничения. Не утверждай, что проверка прошла, если её не запускал. Поддерживай команды установки, запуска и проверок в `README.md`, когда появится приложение.
