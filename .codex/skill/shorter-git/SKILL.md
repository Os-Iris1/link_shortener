# Git в Shorter

## Разрешения

Отправка на удалённый сервер запрещена. Не выполняй `git push`, в том числе для веток, тегов и удаления удалённых ссылок; не обходи запрет через API, плагины, другие команды или инструменты публикации.

Локальная работа разрешена: можно создавать коммиты, создавать, переключать и удалять локальные ветки, выполнять локальные слияния. Дополнительное подтверждение для обычных локальных операций в рамках задачи не требуется, кроме слияния в dev и продвижения в stage: они требуют явного разрешения пользователя после review. Это разрешение не означает необходимость коммитить каждую правку автоматически.

Перед изменениями проверь `git status`, текущую ветку и существующие ветки. Сохраняй пользовательские изменения; не включай посторонние изменения в коммит и не удаляй незавершённую работу при переключении или удалении веток. Перед коммитом просмотри staged diff: уже подготовленные пользователем файлы могут относиться к другой задаче.

## Ветки

Используй проектный Gitflow с ветками `dev`, `release`, `stage`. Не подменяй их автоматически стандартной схемой с `main` или `master`.

Для каждой задачи создай отдельную ветку от `dev`, например `feature/short-topic`, `fix/short-topic` или `chore/short-topic`. Выполняй изменения и создавай коммиты задачи в этой ветке. После реализации выполни необходимые проверки и передай пользователю ветку, результат и проверки для code review. Не сливай в `dev` до явного разрешения пользователя после review. Если review требует исправлений, внеси их в ту же ветку, повтори затронутые проверки и снова предоставь результат для review. Перед каждым коммитом обязательны успешные `go test ./... -cover`, `go test -race ./...` и `go vet ./...` (или `make check`); при недоступной или падающей проверке коммит не создавай. Если репозиторий ещё без коммитов или `dev` отсутствует, не включай все имеющиеся файлы в начальный коммит только ради инициализации процесса; учитывай отдельное разрешение пользователя на начальную настройку.

`dev` накапливает изменения задач, прошедшие пользовательский code review и получившие разрешение на слияние. Когда пользователь определит достаточный набор изменений, проводится глобальное review. Только после него и явного разрешения продвигай указанную пользователем версию из `dev` в локальную `stage`; не выбирай версию или момент продвижения самостоятельно. Если номер версии не указан, уточни его перед продвижением. Наличие ветки `stage` само по себе не означает выпуска версии или разрешения на удалённую отправку. Роль `release` пока не определена: не создавай её и не включай в цепочку продвижения автоматически.

Перед удалением локальной ветки проверь её содержимое и наличие несохранённой в других ветках работы. Не используй принудительное удаление или переписывание истории как побочный способ завершить обычную задачу.

## Коммиты

Используй Conventional Commits:

```text
type(scope): краткое описание
```

Типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`. Область необязательна. Описание пиши по-русски, кратко отражая итоговое изменение; например `build(docker): добавить backend и PostgreSQL`.

Несовместимые изменения отмечай `!` перед двоеточием и поясняй последствия в теле коммита. Группируй связанные изменения, перед коммитом выполняй соразмерные проверки. Не представляй невыполненные проверки как успешные.
